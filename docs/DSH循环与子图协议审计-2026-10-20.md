# DSH、循环与子图：能力边界及协议审计

日期：2026-10-20。检查对象为当前仓库代码、主数据库中的已有任务记录及隔离数据库复现。

## 结论

平台已有通用有限遍历执行能力，不能将目前的卡顿全部归因于 DSH 不会生成循环。问题分布在四个边界：**能力声明与实际实现、发给模型的协议与校验器、前端与后端接口、DSH 会话与平台任务状态**。

当前适合稳定化的目标应明确限定为：**显式网格 → 单层批量子图 → 全点结果 → 分组评价/筛选**。暂不把嵌套循环、状态反馈迭代、收敛求解、任意拓扑规划列为自然语言建图的已交付能力。

本轮仅检查、编写复现脚本和报告，未修改生产校验、运行时或任务状态；没有调用模型、追加额度或注册工具。

## 1. 循环和子图究竟是什么

### 1.1 子图是计算范围与接口边界

子图是一张有自己输入、节点和输出的小工作流。它不是“把节点画在一个框里”，也不自动意味着循环。

外部只能通过声明的输入把数据传进去，通过声明的输出取结果。子图里的节点不能偷偷读取父图的其他变量；外部节点也不能越过子图输出，直接读取里面的任意节点。

当前执行模型没有通用的 `subgraph` 节点类型。子图主要嵌在 `batch/foreach.body` 或 `switch.cases` 中；画布可双击进入这些范围。

### 1.2 当前建图中的循环是有限遍历

例如先列出全部 `(Vin, R_load, fs)` 组合，再让同一张单工况子图对每一行执行一次。每次拿到的当前行叫 `item`，固定共享参数由 `captures` 显式传入。

126 个点意味着**运行时执行 126 次子图**，不意味着让 DSH 写 126 张图或调用 126 次模型。工具生成的并发数也不是运行时批量计算的并行数；当前 batch 的各行按代码顺序执行。

### 1.3 收敛循环是另一种尚未交付的能力

“根据结温更新电阻，再算损耗，直到温度变化小于阈值”需要上一轮状态、更新关系、收敛条件、最大次数、发散/非收敛结果及终止策略。现有有限 batch 不具备这些语义，不能用普通连线回环代替。

计算图中的未声明回环会被判为 `CYCLE`。受控函数也不允许用 Python `while/for` 偷藏工作流循环。

## 2. 当前能力清单

| 能力 | 执行引擎 | 自然语言设计入口 | 注意事项 |
|---|---|---|---|
| 普通多节点 DAG | 支持 | 支持 | 来源、依赖、字典和单位必须明确 |
| 数值笛卡尔积网格 grid | 支持 | 支持 | 输出端口固定为 `rows`；最后一个轴变化最快；至多1000行 |
| 单层 batch 子图 | 支持 | 支持 | 列字典输入、逐行 item、显式 captures、显式输出别名 |
| 每点文字失败原因 | 支持 finite_controls_v2 | 可声明 | 原样保留空字符串与行顺序；当前画布端口推导仍有错误 |
| collection 型 foreach | 支持 | 当前新建图 DSL 不以此为规范路径 | 前端仍有旧版输出命名逻辑，不宜宣称全链路已对齐 |
| switch 分支子图 | 支持 | 当前 DesignPlan 没有对应的专门分支声明 | 各分支输入输出必须一致；不能据引擎支持推断自然语言入口已覆盖 |
| sum/mean/min/max 集合汇总 | 支持 | 当前 DSL 没有专门汇总控制声明 | 新版后端输出 summary，前端仍推导 value |
| 多层嵌套子图 | 引擎递归编译有深度限制 | 不支持当前建图协议中的嵌套循环 | 引擎上限不能当成建图服务承诺 |
| 状态反馈、收敛求解 | 不支持通用节点 | 不支持 | 不得把有限遍历描述成收敛迭代 |
| 任意通用子流程调用节点 | 没有独立通用类型 | 没有 | 当前 body/cases 是内嵌 Workflow |

其他已实施边界：DesignPlan 最多60个计算步骤、4个网格、4个 batch；成员不得重复归属；运行累计节点预算20000；数值数组元素预算100000。batch 堆叠后的数组维数不能超过4。普通数值不能携带任意 NaN/Infinity；缺失推荐列须有明确 `missing_when` 和有效性标记，以 JSON null 编码。单个函数源码上限16000字符。

batch 输入是共享 `batch_rows` 的一维必填数值列。成员输出可为数字、数值数组或**单条字符串**；不支持布尔输出列、collection 输出字段、嵌套文字列表。0/1 判据可按已确认的数值声明表达，不能静默更换已确认接口。

源码依据：`models.py`、`finite_control.py`、`plan_controls.py`、`engine.py`、`numeric.py`、`expressions.py`。

## 3. 现在怎样检查一个任务

| 检查层 | 平台现在检查什么 | 不能据此证明什么 |
|---|---|---|
| 回传封装 | kind 与顶层对象一致，不能提交字符串化 module/patch；原始回传留存 | 代码或方案正确 |
| Schema/声明 | 字段、类型、维度、轴、单位、语义、版本 | 模型物理适用 |
| 控制结构 | grid端口、成员归属、作用域、captures、输出别名、跨图引用和DAG | 数值结果正确 |
| 接口连接 | 每个输入唯一来源、字段映射、形状/单位/语义兼容、依赖一致 | 同名或同单位字段物理上能互换 |
| 受控实现 | AST、库函数、入口/适配器、显式变换声明 | 任意合法 Python 都能运行 |
| 字段依赖 | 计算读取、保护读取、未声明读取、可选字段保护、未用必填字段 | 公式完整正确 |
| 独立样例 | 与人工/可信程序的输出比对；最小输入与额外字段探针 | 全参数空间、器件实验或工程认证 |
| 整图运行 | 输入保护、实际计算、输出类型/维度、运行预算、追踪与快照 | 满足需求中没有写出的技术标准 |

无独立样例的普通候选可以保持“未验证”，不等于已跑过数值验收。**但包含显式变换的候选目前要求至少两组独立样例**，这属于额外门槛，应在生成前明确显示，而非模型提交后才暴露。

独立预期输出不应提供给生成候选的 DSH。现有 formula 上下文会移除 examples 的 outputs，仅发送验证输入，此边界应保留。

## 4. 本次确认仍存在的缺口

### P0：DSH 结束但平台没有有效提交，状态不能闭环

隔离复现结果：DSH `running=false`；平台仍是 `awaiting_worker`、`active=true`；继续操作不允许，继续接口也拒绝。

`design_progress.Progress.refresh()` 只记录观察值，不驱动任务进入明确的可恢复状态。新加的顶层参数/运行时指纹检查能够阻止错误提交，但返回 `stop_required=true` 时仍可能没有平台失败回执，因此不能认为上轮传输修复已经解决了整个状态生命周期。

队列把这些调用计为在途；若长期不闭环，会占用并发名额。不能简单凭一次 `running=false` 自动重发，因为仍可能有排队、查询瞬态或迟到回传。

应补：核对同一 call_id 的会话终止事件、未完成队列、已收回执和观察宽限期；无有效提交时形成 `ended_without_submission` 或明确的待核实状态。提供关闭旧调用、复检候选、使用剩余额度恢复等操作。关闭后旧结果只能留存，不能应用。

### P1：发给 DSH 的正式 Schema 与所要求的提交类型不完全对应

复现一：`required_result_kind=plan_delta` 时，`schemas` 仍只有 `blueprint`，没有对应 delta Schema。文字说明虽描述 delta，模型拿到的机器契约仍不完整。

复现二：`blueprint_schema().properties.port_defs` 只有 object 与文字描述，没有描述其成员结构；dtype/shape/axis_names 等实际必需条件仍主要依赖编译器后验检查。

应补：每阶段只发送当前唯一提交类型的精确 Schema；补齐紧凑 Port 和变更操作的正式声明；用相同样本自动对照“对外 Schema 接受”和“内部编译接受”。单位/物理语义等无法完全用 JSON Schema 表达的约束，仍需显式列出独立检查规则。

### P1：数值语言限制没有在首次请求中完整交付

首次 formula 上下文发送函数名清单，未包含 `numeric.catalog()` 已有的关键字签名、变换标记与预算等完整信息。详细数组逻辑规则通常出现在已有失败候选后的 `adapter_repair()`。

因此 DSH 写出常规 NumPy 的 `&`、`numpy.all(...,axis=...)`、推断维度 reshape 或未经登记的函数，会遇到受控语言拒绝。限制本身可以合理，但必须事先明确，不能靠反复失败来学。

应补：从运行时注册表生成首次可读的语言规范、函数参数、禁止项、限制、变换及样例门槛；不要再维护几份互相覆盖的提示词。

### P1：已知程序错误仍可能被分到“依据不足”

隔离复现：`UNDECLARED_TRANSFORM /module/transforms` 被分为 `uncertain`、`automatic=false`。缺少 reshape 变换声明是已定位的实现合规问题，不能一概要求用户补物理知识。若实际缺少独立样例，则应明确指出缺少的是验证材料。

`RESULT_ENVELOPE` 又统一进入 needs_confirmation，导致纯包装错误与真正的接口/物理变更共用停止路径。不能为解决包装问题开放任意改公式，也不应让包装问题永远堵住继续操作。

应补：逐错误码标记责任方、允许修改路径、需要的证据、恢复动作；“局部包装/实现修正”“接口修订确认”“物理资料”“平台故障”“传输状态”分开。

### P1：前端和后端有三处控制端口不一致

本轮直接调用实际前端 `types.ts/ports()`，与后端正式 interface/compile_workflow 比较：

| 对照项 | 后端正式结果 | 当前前端推导 |
|---|---|---|
| batch 成员 string 字段 | array dtype=string | array dtype=float64 |
| foreach v3 命名输出 | assessment（随原端口名） | results |
| aggregate v3 输出 | summary | value |

这会造成画布端口展示和用户连接依据错误，不代表已有正确后端工作流必然算错。应由后端一次生成权威接口供画布使用，或使用同一规范生成两端实现，并增加逐端口一致性测试。

### P1：恢复路径不统一，仍有任务专用内容

现有普通 continue 拒绝 needs_confirmation。公式包装错误保留的是字符串，不能当作完整 Module 直接重验。当前 `/formula-recovery` 后端存在，但设计器没有对应调用入口，且这个函数内仍有 Vin/R_load、交错分组与排序规则的定向提示。它不能作为所有新任务的通用恢复机制。

旧蓝图回放、端口修复、接口使用修订、公式重验、追加次数是不同入口，用户与调度器还缺少统一的“此状态有哪些合法下一步”表示。

应补：后端返回权威 actions 列表（包含是否调用模型、作用范围、前置条件、剩余额度与确认要求），前端按列表呈现；删除通用恢复器中的任务特例。重试、恢复剩余额度和新增额度明确区分。

### P2：新工具生成仍要求 DSH 重复整个 Module 契约

`automation.py` 的已有自然语言工具修改路径已经有 implementation_patch_v1，但 `designs.py` 的新工作流补工具仍回传完整 Module。数组、循环成员及语义元数据多时，重复契约增加回传长度、转义和无意改接口的风险。

应复用“冻结接口 + 仅提交实现”的模式：新工具候选携带步骤/契约哈希与源码、实现类型、适配器和变换说明，身份/版本/已确认接口由平台复制并校验。不是让平台替写公式，更不能从非法字符串中猜着修补代码。

### P2：通用分组排序被迫变成复杂受限数组程序

LLC 排序任务与循环成员不同，它消费的是循环外全点数组。当前语言不允许一般 Python 循环，常规位运算掩码和部分 NumPy API 又不支持，容易把简单的分组选择写成复杂矩阵运算。交错分组、完全平局、无合格候选尤其容易出错。

建议将按明确键分组、稳定排序、计数和按有效性选择等数据操作做成可复用标准工具。分组键、优先级与无候选策略仍由已确认需求决定，不自动替用户决定“最优”。目前不能把这些工具描述为已经交付。

## 5. 已修复的旧问题与仍未验收的部分

已确认可工作：grid 的正式端口与轴契约；单层 batch 的作用域；126行逐点文字及空字符串保留；保护条件与实际计算读取的区分；带有效性声明的缺失推荐列；顶层参数检查、指纹文件名和桥接检查；程序按明确连接组装有限子图。

已运行的复现：电流网格铜损 `[-2,0,2]`、R=0.5，输出 `[2,0,2]`；126点文字检查保留全部126条原因及空文字。

这不表示真实 LLC 全链已经验收。当前这批是14个计算步骤，8个已匹配，5个候选待核对注册，1个排序任务暂停5/5。排序四组独立参考仍未完成正式验收。当前没有在途设计任务；历史“DSH停了而平台仍等待”的问题由隔离复现确认，不能说现在主任务正在运行。

## 6. DSH 应怎样操作

1. 平台先提供版本化能力清单：本次允许的控制结构、语言、预算、输出类型和恢复动作。超出支持范围时说明缺哪项能力，不进入无意义生成循环。
2. DSH 读需求，给出计算步骤、明确的输入来源与适用条件；不提前索要全部运行数值。
3. DSH 只声明 grid 轴、loop 成员、rows、captures、输出别名。平台从这些声明生成正式 body 与控制接口。
4. 循环成员只针对当前 `item` 写单工况公式。固定设计参数走 captures；外层节点从 loop 的导出别名读取数组。
5. 用户确认语义与接口后冻结。DSH 每次只写一个缺失工具的实现，不能为了过检查改单位、必填性、公式、输出或保护条件。
6. 程序错误进入限定路径的实现修正；缺验证资料时列出精确缺项；改变已确认内容则派生并展示差异后确认。保留成功工具与原额度，不从头生成。
7. 工具核对注册后，由平台确定性编译接线。已明确的结构不再交给 DSH 重写一遍 Workflow。
8. 先做小网格整图检查，再做原需求的完整工况及可信程序对照。样例、运行数据与生成要求分开管理。

LLC 的推荐职责分界：

```text
外部输入：Vin数组、负载数组、频率数组、设计参数、限制
    ↓
平台 grid：确定性生成每一行
    ↓ rows
平台 batch 子图：每行执行同一组单点公式工具
    输入 = item + 明确 captures
    输出 = 每点预测、应力、损耗、判据、中文原因
    ↓ 全点列数组，保持顺序和 case_id
循环外：汇总 → 按确认规则分组筛选 → 展示推荐与无候选状态
```

## 7. 修复顺序及完成标准

### 第一批：先解决状态与契约不一致

- **任务状态闭环**：覆盖正常回传、工具参数拒绝、桥接失败、模型无提交结束、网络未知、服务重启、用户停止及迟到回传。每个状态有明确恢复动作，不重复发送，不静默重置额度。
- **前后端控制接口统一**：修复上述三项并用后端契约逐项对照；画布端口与运行接口一致。
- **Schema 与初次请求对齐**：请求什么提交类型就发送什么 Schema；数组声明、函数签名、变换和验证门槛一次给全。
- **错误分流覆盖**：已知实现/包装问题可限定范围修复；真实语义、接口变更仍确认；平台故障不让 DSH 改检查器。

### 第二批：减少重复生成和人工找按钮

- 将公式工具生成改为冻结接口上的实现候选；复用现有实现补丁经验，不混淆旧协议。
- 统一恢复 actions、回执和尝试编号；显示当前操作对象，区分查看记录、复检、恢复和追加。
- 将排序恢复中的任务特例迁回该任务的上下文证据；构建通用的数据处理工具能力。

### 第三批：证明新任务也不会重复踩坑

- 从不含 LLC 专用工具与任务的隔离库开始，完整重建同一需求，禁止手改候选，禁止隐含额外额度。
- 使用另一条有限扫描计算链作迁移验证，不能只证明 LLC 特例能跑。
- 验收矩阵覆盖：单点、多点、轴顺序、共享输入、跨域引用、不同数值类型、126点文字、空/超限输入、数组输出、单点前提失败、无合格候选、交错分组、平局规则、过期版本、重复回传、无回传结束、网络未知、重启恢复。
- 统计首轮协议通过率、修正次数、模型耗时、平台检查耗时、人工补充次数及无法恢复状态；不能只统计最终“成功”。

不必先扩展嵌套或收敛循环。先让已经声明支持的一层有限子图做到闭环和可复现，再单独设计收敛迭代的状态模型及失败语义。
