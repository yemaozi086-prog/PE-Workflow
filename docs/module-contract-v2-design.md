# 下一阶段：数组契约、模块适配与 DSH 注册闭环

状态：设计稿。用户已确认 Q16–Q20 的边界；本文件不表示运行中的 1.0 引擎已支持这些扩展。当前接口仍以 `models.py` 与 `/api/schema` 为准。

## 1. 已确认范围

- 外部参数仍只有裸参数和扁平字典。裸参数包含单值或数值数组；字典字段可以是裸数组，不允许外部嵌套字典。
- 上传对象是单个 .py 纯计算函数。允许参数名、字典结构、单位、返回形式不同。复杂类或多文件工程由 agent 先整理为支持的单函数，平台不直接接纳。
- 数学能力包括 math、NumPy 及明确登记的 SciPy 功能。仍保持禁止任意上传代码 eval/exec/importlib 的当前项目约束；需要扩展现有解释执行器的签名、数组和受控库调用能力。
- 自动适配仅包括显式声明的改名、取值路径、组装、单位换算。转置、重采样、周期截取等改变数据口径的操作，必须作为有前提、有样例的显式变换。
- 未确定语义集中追问一次；未答清的关键项保留待定，不执行、不登记为可替换模块。
- 平台准备任务上下文和确定性计划，DSH 依据上下文集中写候选代码。

## 2. 三份分开的声明

1. 参数定义库：语义概念、单位、数组轴、别名和定义来源，可新增，改变已有含义时创建版本。
2. ADBB 外部契约：模块对工作流公开的输入、输出、适用条件和声明版本。
3. ADBB 内部适配：原函数入口、参数传递、原字典组装、返回路径和单位转换。

参数名用于定位，受控概念用于匹配。别名帮助检索和提出候选，不作为已确认含义。注册后的模块契约引用并冻结参数定义版本；不得通过修改中心词表悄悄改变已注册模块。

建议后续协议将 `kind` 与值类型分开，避免 scalar/array/flat_dict 混在一个维度。2.0 协议需要显式版本和 1.0 导入迁移器，不原地重解释已有 JSON。

```json
{
  "kind": "bare",
  "value_type": {"dtype": "float64", "shape": ["N"]},
  "semantic": {"quantity": "current", "characteristic": "instantaneous", "scope": "primary"},
  "unit": "A",
  "axes": [{"name": "time", "coordinate_ref": "time"}],
  "required": true
}
```

上例是拟议的数组字段；time 为同一契约范围内声明的坐标参数。单值使用 shape=[]。扁平字典使用 kind=flat_dict + fields，每个字段仍是裸参数声明。

### 数组校验

- 校验 dtype、维数、矩形结构、有限数值与元素数量预算；禁止 object 数组和未声明的参差数组。
- 符号长度在所属契约/调用范围内统一，例如 time 和 current 的 N 必须一致，不把所有模块中的 N 当成同一个全局符号。
- 静态检查固定形状、维数、轴含义；运行期检查符号长度和实际坐标。无法静态证明一致时，明确给出运行期条件。
- 时间数组检查长度匹配、递增性及采样相关前提。相同长度和时间单位不能证明两条波形拥有相同采样网格。
- 矩阵记录每一轴的工况/通道/物理量含义；禁止在连线时暗中交换轴、广播、截断、补点或重采样。
- 波形的 RMS、峰值、周期平均等是显式计算模块，不是端口匹配器的同义词处理。
- 首阶段小数组以声明过类型的 JSON 数组传输，运行边界转换为数值数组。大数组附件和复杂数值类型留扩展接口，不伪装成控制流 collection。

## 3. ADBB 调用边界

外部输入校验 → 输入适配 → 单函数计算 → 输出适配 → 外部输出校验。

保留原上传源码与指纹；适配描述为数据，运行时不再由模型猜测。原程序内部的嵌套字典可以通过路径组装和取值映射对外公开为裸参数或扁平字典，外部类型约束不强加到原始返回结构。

```json
{
  "entrypoint": "legacy_loss",
  "arguments": {
    "freq_khz": {"from": ["inputs", "fs"], "conversion": {"from_unit": "Hz", "to_unit": "kHz"}},
    "current_info": {"assemble": {"Irms": {"from": ["inputs", "i_rms"]}}}
  },
  "returns": {
    "p_loss": {"from": ["return", "result", "loss_mw"], "conversion": {"from_unit": "mW", "to_unit": "W"}}
  }
}
```

原入口需显式指定，不默认选源码中第一个函数。首阶段允许一个入口函数和受控导入；类、外部工程文件、文件/网络操作、无法静态枚举的动态依赖返回不支持清单。是否支持某个 SciPy 调用由解释器的函数注册表决定，不以 import scipy 即全部授权。

适配检查应覆盖原函数参数是否全部满足、字典读取键、返回所有分支、路径是否真实存在、单位/形状、默认值来源。静态分析无法证明的内容用测试样例补充，并标明证据范围。观测过一次输出不能证明所有分支都会产生该字段。

### 计算库扩展

建立 NumericFunctionRegistry：每项记录稳定 ID、导入对象（平台代码登记）、函数签名、参数类型、返回类型、纯计算限制、输入规模预算、确定性说明、固定库版本与验证样例。外部上传源码只能引用已登记功能。

实现顺序建议为：数组创建和索引/切片、基础数学与统计、矩阵运算；随后根据首个真实迁移函数选取 SciPy 数值积分、线性代数等具体函数。需要回调、返回可执行对象、读写文件或动态加载的 API 暂不自动开放，逐项审计后再扩展。

不要把执行器目前的 Python 语法子集承诺成“任意单函数都兼容”；分析阶段必须返回 supported/unsupported_features。形状/口径变换即便代码可以执行，也必须声明变换目的与前提。

## 4. 能力目录与替换判定

模块摘要包含：模块族与版本、capabilities、适用拓扑/调制/器件、外部输入输出、适用范围、额外依赖、来源、验证状态、可用样例、契约和源码指纹。

能力标签用于找候选；替换报告由平台针对当前节点生成。报告覆盖：

1. 当前上游能否满足新模块的全部必需输入，默认值是否显式且符合用户要求。
2. 新模块是否覆盖当前下游实际消费的全部输出和字段，是否需要显式端口地址映射。
3. 物理语义、单位、数组轴、单器件/整机、单工况/跨工况统计口径是否一致。
4. 当前工况是否在新模块适用范围，是否有尚未验证的范围外工况。
5. 指定锚点、适配前后对照和物理不变量是否通过。接口兼容不自动等于数值等价。

建议状态：direct、adapter_required、needs_inputs、domain_conflict、incompatible、unknown。报告列出证据、输入/输出映射、变换、缺口和测试范围，不只输出相似度。

```json
{
  "target": {"workflow_id": "design_a", "revision": 4, "node_id": "switch_loss"},
  "candidate": {"module_id": "temperature_loss", "version": 1},
  "status": "needs_inputs",
  "missing_inputs": ["Tj"],
  "covered_outputs": ["p_total"],
  "unresolved": ["新模型的适用温度范围尚未声明"],
  "can_apply": false
}
```

目录中登记 declared_replaces 只能表示作者意图，不可覆盖平台判定。某模块在一个工作流里可替换，不代表可全局替换其他工作流中的所有同名节点。

## 5. 平台主导的注册流程

状态：draft → analyzed → needs_information（如有）→ validated → registered。

平台分析结构事实和代码支持范围，聚合关键语义问题。agent 在一个问题批次中向用户提问；答案绑定到对应字段和来源。没有得到答案的关键字段停留在待定状态；新发现的独立关键问题不能通过猜测强行结束流程。

agent 提交的候选包含原始源码、入口、外部契约、适配声明和验证样例。平台检查后登记不可变版本，并返回能力摘要和针对已知目标节点的替换报告。登记模块与修改工作流分开：成功登记不意味着已经替换。

工作流应用应使用完整替换计划和 expected_revision；对候选图整体试读并运行指定样例后，提交单笔新修订。任一检查失败，旧图不被部分改写；已登记候选模块可留存为后续候选。之后的正式计算和优化读取冻结的新图，不能重新取全局默认图。

## 6. DSH 上下文与工具

DSH 注册有限的通用平台工具，ADBB 登记在平台目录。新增 ADBB 后刷新目录版本戳并使检索缓存失效，不为每个函数增加一个 DSH 工具。

新增两个聚合工具作为主要入口（拟议接口，尚未实现）：

- prepare_module_change(workflow_id, node_id, request)：返回完整上下文、已确定要求、集中待答问题、建议范围、验收样例与 context_id。
- submit_module_candidate(context_id, source, adapter, contract_changes)：提交候选，平台检查并返回注册/替换报告或可操作诊断。

context_id 绑定工作流修订、模块/参数定义版本及源码指纹。提交时检查上下文是否过期，不依据陈旧图应用修改。

上下文包必须包含：当前任务目的、用户已确定修改、目标节点与所有相关控制分支、完整单函数源码与受控依赖、外部契约、内部映射、上游实际可提供的数据、下游实际消费字段、适用条件、输入样例、旧结果、锚点/容差、不变量、已知失败、允许修改范围及禁止假设。

数组先给形状/轴/统计摘要；需要完整数据时通过数据 ID 读取，避免上下文被大量波形数值淹没。每条信息标记为事实、用户要求或系统建议。函数源码与相关声明完整提供，不能为节省上下文漏掉实际计算依赖。

其余工具为：参数定义查询/登记、module_search/inspect、replacement_plan、workflow_apply_plan、workflow_run。DSH 固定规则见 `dsh-agent-rules.md`。这是一份供后续插件实现的规则稿，本轮没有修改用户 DSH 配置。

## 7. 迁移实施顺序与验收

| 阶段 | 工作 | 核心验收 |
|---|---|---|
| M1 | 2.0 参数定义、语义词表、数组/轴校验、1.0 导入迁移 | 正确波形/矩阵可传；长度、轴、单位错误准确阻断；旧示例结果不变 |
| M2 | 单函数分析、内部适配、受控 NumPy/SciPy 执行 | 不同参数名/字典结构/单位/返回路径，适配后与原样例一致；不支持项明确拒绝 |
| M3 | 能力检索、适用范围、替换报告、原子图更新 | 候选能指出新增输入和下游缺口；未满足条件不能应用 |
| M4 | 聚合上下文工具与 DSH 插件 | 一轮信息补全后完成登记、替换、验证；失效上下文拒绝提交 |
| M5 | 完整电流/损耗/约束链逐项迁移 | 与原固定流程的可信输入、中间值和最终值对照，保留逐器件完整数据 |

旧草稿优先迁移结构扫描、受控词表/证据、源码依赖检查、适配缺口报告和运行观测经验。原有按名字兜底、默认选择首个函数、自动将统计口径当同义词、只检查适配器一个输入、就地覆盖已注册契约等行为不作为新协议默认行为。

更完整的优化变量/目标/约束任务协议在上述闭环之后完善，PPO 与物理收敛迭代再后续扩展。
