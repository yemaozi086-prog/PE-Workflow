# 工具补齐与恢复交互决策

日期：2026-10-18。讨论深度：深挖。实现前继续确认重要边界。

## 已确认

1. 声明缺失时，根据已有方案整理补充草案，逐字段显示来源与差异；用户确认后派生修订并重新检查，再使用剩余额度继续。无依据的字段集中询问。
   理由：避免重复录入，同时不把推测写成已确认语义。
2. 明确属于候选格式的问题（如 EXPRESSION_OUTPUTS）自动进入候选修正，保持已确认公式、接口、约束和验收答案。沿用剩余额度与同类错误连续两次停止规则；无法确定归属时暂停。
   理由：程序问题由内部循环处理，不转嫁给用户判断，不削弱验证。

3. 旧任务先只读重新分类，展示恢复清单与剩余额度；用户统一确认后继续。保留旧失败记录、候选与额度，不重新生成已通过工具，不自动注册。
   理由：恢复可预览、可追溯，避免重新建任务丢失进度。
4. 明确结构化声明可由程序复制；需要模型解释时，调用计入该步现有总额度并预先说明用途。耗尽后允许手动填写或明确批准追加，不另设隐藏额度。
   理由：避免整理资料成为绕过调用限制的通道。
5. 有依据的字段可集中确认；歧义字段逐项询问，仅暂停相关步骤。公式、必填性、字段和保护条件的变化另行展示并确认。
   理由：支持局部推进，不以补充语义名义修改已确认计算契约。

## 已批准的实施与验收范围

- 分流明确候选格式错误、声明缺失、依据冲突和平台故障；仅有确定依据的候选错误进入自动修正。
- 声明草案显示字段路径、原值、新值、来源和待确认项；接受后派生修订，执行受影响检查。
- 保存说明不等于恢复执行。按钮、响应与进度准确显示保存、等待确认、已排队、处理中和失败原因；不以模糊的“继续”覆盖不同操作。
- 旧任务恢复清单不自动消耗调用；明确确认后才调度可恢复步骤，仍遵守原额度及重复错误停止规则。
- 重复提交幂等；过期修订拒绝并提示刷新；页面关闭或服务重启后可恢复状态；发送结果未知时不自动重发。
- 对现有 Buck 的 evaluation 和 cap_esr 任务验证恢复路径，保留原记录；测试格式修正、语义缺失、无依据字段、额度耗尽、重复错误、重复提交、修订冲突与恢复中断。
- 候选检查、独立数值验证和注册状态分别展示，不自动注册或运行完整工作流。

## 待定

无影响本轮实现的重要产品边界待定。用户已批准上述范围。

## 实现与验证

- 恢复清单只读，确认时校验队列及所有步骤修订与预览哈希；恢复收据防止重复提交。同类错误停止及调用额度保持。
- 当前语义草案只复制字段原有 description，缺少来源时留空供用户填写，不调用模型猜测。确认只允许填列出的空缺 quantity 字段；其他契约变化仍走方案修订。
- 新声明修订保留原任务、事件、样例、调用预算、版本预留；更新队列指向。允许部分补齐，剩余缺项继续阻塞相关步骤。
- 恢复会保留旧配置历史，并明确采用当前平台配置；不重新生成已通过候选，不自动注册或运行。
- Buck 真实数据在小型隔离副本中验证：cap_esr 明确分流为候选修复，保留已用 1 次、剩余 3 次；evaluation 的 8 个字段均从已有说明形成草案，确认后进入待生成。未调用模型，原任务数据不变。
- 后端全量回归 343 项通过；前端构建通过。完整磁盘副本尝试因磁盘不足中止，删除了本轮不完整副本，原数据库及完整备份保留；后续验证使用独立的小型测试数据。
