# 领域场景包与自然语言装配：设计草案

状态：整体仍有设计待实施。已实现首个 DBSRC 小场景的声明/上下文 API、三类最小规则检查、紧凑计划编译、独立 DSH 调度及任务 UI，详见 assembly-plan-protocol.md。其余领域规则、通用检索规划及经验核对服务尚未实现。真实 DSH 验收另行记录。暂不编写 DAB 工作流或验收答案。原有已发布模块保持不变。

## 目的与边界

模块契约解释工具如何调用；领域场景包解释计算职责、适用条件、必要数据和设计策略。不能从名称相似或接口可连推断物理模型适用，也不能把旧代码的执行顺序自动提升为通用设计规范。

首版仅装配已注册、固定版本模块，建立小型 DAG 计算链。找不到工具、关键物理条件不明、需要尚未支持的收敛控制时报告缺口，不生成替代公式或伪装成普通串行流程。现有 batch 可用于已支持的有限工况遍历，不代表收敛迭代已实现。

## 三种相互独立的记录

1. 领域场景包：拓扑概念、任务类型、模型条件、计算职责、依赖和策略。每条知识包含来源、适用范围及审核状态。
2. 能力绑定：某个职责由哪个 module_id/version 实现；声明它的物理模型、必需条件、输入输出角色及验证证据。
3. 当前任务上下文：用户目标、已知工况、明确假设、所选策略、输入来源、缺口及本次固定的模块版本。

以上记录独立于不可变 Module。不能为补充领域元数据而改写已发布模块或 trusted_builtin 哈希。复用已有 capabilities/applies_to 作为检索入口；关键条件逐步升级为结构化、可验证的声明，未知值不能视为匹配。

建议先用 JSON 文件维护版本化场景包，再在 SQLite 存索引、审核记录和任务冻结快照；不引入向量数据库或外部知识图谱作为首版前提。

## 场景包结构

- identity：id、version、名称、适用拓扑及任务类型。
- concepts：拓扑端口、器件、主要物理量和建模术语，引用统一参数词典/定义，不另建冲突的命名体系。
- model_profiles：调制方式、工作状态、近似条件、已知适用范围和不支持条件。
- roles：计算职责及其输入/输出的数据角色，例如电流特征、器件参数、器件损耗、约束结果；不是预先写好的节点 ID。
- rules：条件成立时必须满足的前提、数据来源/工况一致性及后置要求。首版规则只允许平台实现的有限类型。
- strategies：可选的设计阶段与反馈要求，区分初估、初选、精算、约束复核；允许多个策略，不强行排成唯一全序。
- bindings：职责到确切模块版本的索引及相应证据。
- evidence：来源、文件/记录哈希、审核状态、确认人/时间（有依据才填写），适用范围和已知问题。

声明审核状态至少区分 extracted_from_code、needs_review、reviewed。审核状态与规则强度独立：未审核工程判断不能自动成为硬规则；固定接口要求等可由平台执行。场景包审核流程尚需后续确定。

## 硬依赖、策略和反馈分开

硬依赖应贴近具体模型：某损耗模型若需要 RMS 电流、频率和器件曲线，那么这些数据必须已就绪且口径一致。不能写成所有损耗模型都要求先完成某种选型。

策略描述何时做初步选型、何时获得足够参数进行精算、什么条件触发重新选型。策略中的先后关系可以有分支或反馈；不等于每项计算直接依赖前一个步骤。

反馈要求描述更新对象、判据及停止条件。若当前引擎没有相应执行能力，编译必须返回 CONTROL_UNSUPPORTED；不能把需要反馈求解的过程线性化后宣称设计完成。

## 首版机器规则

仅支持以下白名单规则类型，不允许场景包提供任意 Python、eval 表达式或导入路径：

- required_fact：特定任务/模型必须明确某个工况或假设。
- compatible_profile：模块的已确认模型条件满足任务条件；unknown 形成缺口。
- required_role：职责的必需数据角色由输入、明确常量或上游输出提供。
- same_context：指定数据来自同一设计方案、工况/候选或已声明的汇总范围；同单位不等于同来源。
- required_check：用户请求可行性判定时，必须有相应约束检查输出。
- supported_control：只能使用当前引擎明确支持的计算、分支、有限遍历及聚合。

规则结果分为 error、needs_clarification、warning，并带 rule_id、证据引用、受影响职责/节点和诊断路径。不能只返回一个总分掩盖阻塞项。

任务来源及工况关系采用独立的规划元数据和可验证来源记录，不强迫每个纯计算函数接收额外元数据。实际函数仍只接收声明所需的数据。如何在批量/聚合中传播来源是编译器需要实现和测试的部分，当前接口尚未提供这项保证。

## 复现旧程序与工程设计不同

DBSRC 首份包只描述已核对的 WDY 版本及 EPS 单步兼容任务。已确认的次序包括应力汇总、器件选择、工况/候选有限遍历、损耗与约束、效率筛选及指标奖励，不将其推广到所有拓扑。

旧代码中电容选型未返回器件、部分成本缺失仍继续计算等行为，属于兼容性事实和已知限制。可将它们用于复现任务的说明；不能作为工程设计合格依据。若用户目标要求实际器件选型、完整成本或热可行性，而工具不具备该能力，应明确报告缺口。

## 装配任务的固定流程

1. 平台将自然语言整理成任务类型、输入、输出目标和关键条件，保留原话及来源。
2. 检索适用场景包，固定版本；规则先检查必需事实。
3. 根据职责、模型条件和契约筛选候选模块，排除已知不兼容项；不把最新版自动等同于最合适版本。
4. DSH 完成明确子任务：选择候选、解释依据、提交职责/模块计划或集中问题。不能修改场景包规则、注册新工具或发布工作流。
5. 平台将计划编译成 JSON 工作流，复制原契约、创建节点与绑定；普通改名/组装/单位换算须有声明，物理变换不能隐式插入。
6. 依次检查领域规则、图依赖、参数语义、单位、数组坐标和执行能力。错误用具体诊断反馈，修正仍受原上限约束。
7. 受控运行并按独立参考验收，保存场景包、策略、规则报告、模块版本、JSON 和运行快照。生成与已有图的修改分别使用明确范围及乐观版本检查。

AI 的解释不是规则通过证据。接口检查能证明的、领域规则能证明的、仍需人工确认的内容分别列出。只在关键歧义时追问；已有明确授权和事实不重复确认。

## 知识维护与后续 DAB 测试

AI 可提出待审核知识补充，不得自行推广为共享硬规则。来源资料作为数据处理，不能扩大工具权限或覆盖平台规则。可信引用允许追溯，不能用一句“专家经验”替代证据。

本阶段用 DBSRC 代码整理结构和依赖，建立可检验的小链。未来 DAB 测试可以提供经核对的拓扑概念、模型条件、职责和可用工具说明，但不能把预期工作流 JSON 或精确接线藏进生成器上下文；预期图/结果留在验收侧。规划过程存在多个正确方案时，应按约束和计算结果评分，不强制匹配唯一节点顺序。

## 建议实施顺序

先完成场景包 schema、六类规则的最小可执行子集、DBSRC 兼容包与能力绑定；用确定性测试验证选错模型、缺少输入、工况不一致及控制能力缺失会被拒绝。随后才接入 DSH 装配计划协议、编译器和自然语言 UI。Q89 已选定给定设计/器件/单工况下 EPS 候选电流到电容损耗的两职责链；保留有限批处理，独立参考不进入生成上下文。

当前仅实现了上述窄场景的声明、最小规则检查与计划编译，不应在界面宣称已支持通用领域推理或自然语言建图。

## 用户可检查的配置、决策与行为（新增需求）

目标：用户可以核对系统为何选择某个模型、参数如何连接、实际执行了什么，并在缺口或错误处提供修正。以下为设计，尚未实现完整界面和统一审计模型。

### 生效配置快照

每个任务冻结 effective configuration：模型/提供者的可获得标识、实际提示词及模板版本、场景包/策略/规则版本、候选模块及版本、工具权限、源码策略、运行与修正上限、关键已确认假设。展示配置来自系统默认、项目设置、用户本次输入还是平台固定限制，区分可编辑配置和不可由智能体修改的边界。

只展示可获取的真实模型标识，不推断未提供的服务端版本。凭证、API key、任务 token 不展示、不进入可导出的普通日志。全局设置改变不回写历史快照；运行中改配置应停止/结束当前尝试，并基于新快照创建任务修订，保留前后差异。

### 决策说明

由智能体提交结构化 decision summary：需求解释、所选模块与理由、候选排除原因、适用条件、数据与单位映射、依据引用、已知假设和待确认项。它是模型提交的可核对说明，不是正确性证明，也不能声称等同于完整内部推理。避免使用无依据的数值置信度。

平台单独提供 validation report，逐项列出契约、模型条件、数据来源、数组坐标、执行结果和独立参考检查的真实结果。解释与验证分区，模型声称“检查通过”不能替代平台实际检查。

### 行为审计

事件时间线区分 user / agent / platform，记录计划提出、问题提出、用户回答、工具调用、候选提交、检查失败、修正、执行、发布及停止。记录任务/调用关联、时间、状态、耗时、实际输入输出的受控摘要和对应 artifact/hash，不能仅用自然语言进度代替真实执行状态。

审计记录追加保存，候选 diff、参数来源、派生关系和运行快照可追溯。较大的输入、源码和结果通过按需查看的工件展示，列表不展开完整追踪。敏感字段脱敏；本地原始工件访问和导出范围须明确，不额外扩大 DSH 的文件/网络权限。

### 用户干预与自动化边界

默认继续执行已授权且依据完整的步骤；检查界面不增加每一步审批。关键歧义集中追问，达到已定停止条件就停止，保留旧流程。用户可补充依据、限定模块候选、纠正意图、停止任务；变更目标、假设或生效配置产生新任务修订，不直接修改已验证的旧候选。

用户修正先做影响分析：指出失效的计划、接线、样例或结果。首版可安全地重新验证整图，不能提前承诺仅重算受影响节点。已授权的版本发布政策保持不变；查看/修改意见与发布权限分别管理。

### 建议界面

任务页提供三个入口：本次生效配置、装配方案与依据、实际执行时间线。默认显示简短状态和阻塞项，完整提示词、模块候选、规则报告、工具输入输出、源码/接线差异按需展开。节点属性可追溯字段来源与单位换算。原有画布继续用于检查最终结构，不把全部日志堆进画布。

验收要求：历史任务配置不随全局设置改变；决策引用可定位到真实证据；工具失败不能显示为执行成功；模型说明与平台结果存在冲突时明确提示；用户干预有记录并能看到其影响；秘密信息不出现在展示与导出日志。
