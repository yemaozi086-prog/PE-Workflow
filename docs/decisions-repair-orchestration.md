# 自动修正与信息补充：决策记录

日期：2026-10-18。本文记录 grill 决策；用户随后批准实施。当前实现范围、验证结果与尚未覆盖的入口见 [repair-orchestration.md](repair-orchestration.md)，不将讨论结论等同于全部验收通过。

## 已确认

### Q1：自动修改范围

结论：智能体内部循环只能修改任务候选代码，以及允许修改的工作流声明。平台自身故障应停止受影响任务并保留诊断，不能由任务智能体修改平台后端、校验器或执行引擎。

理由：避免通过修改验收规则或基础设施来消除报错，破坏固定验收依据。

### Q2：公式与独立样例冲突

结论：发现公式与独立样例存在有依据的冲突时，暂停并集中询问用户；用户确认后再继续。智能体不得自行修改验收答案。

理由：候选代码可能为了迎合错误答案而偏离用户公式。仅有数值不一致还不能证明依据冲突，需区分候选代码错误与验收依据冲突。

### Q3：保留决策记录

结论：在项目 docs 中记录本轮结论、理由和待定问题。

理由：作为后续实现与验收依据，避免反复改变已经确认的边界。

### Q4：错误分流责任

结论：平台依据错误代码、执行记录和验证证据决定自动修正、询问用户或停止；智能体可以提出解释，但不能凭主观判断接管调度。无法判定时暂停，集中询问并说明缺少的证据。

理由：区分可修的候选错误、信息缺失、依据冲突与平台故障，避免把所有失败都变成代码重试。

### Q5：补充信息与额度

结论：补充信息后使用剩余修正额度，不静默重置。额度耗尽后，必须由用户明确批准追加；提交界面应说明继续内容和剩余次数。

理由：避免通过不断追问和补充信息绕过重试上限。

### Q6：按影响范围恢复

结论：只重做受影响的验证阶段。补充信息若改变公式、输入输出或约束，先派生新修订、展示差异，由用户确认后继续；保留原记录。

理由：既避免无关步骤被重复生成，也避免未经确认改变已冻结的计算依据。

## 沿用此前边界

- 最多修正 3 轮；同类错误连续出现两次提前停止。
- 停止时保留候选、诊断和失败原因，原工作流继续可用；超出额度需要用户批准。
- 缺失信息集中追问，不擅自推断物理含义、单位或验收答案。
- 确定的声明映射由平台处理；没有唯一、明确对应关系时不能猜测。

### Q7：暂时无法补充资料

结论：保存待补充任务，列出缺失信息、用途及可能的资料来源，以后补充后恢复。缺少独立验证时可保留明确标记的未验证候选，沿用探索运行边界；缺少关键计算语义时不得猜测运行。

理由：缺少验证证据与缺少计算所需语义是不同状态，不能混为一谈，也不应让用户重新开始整个任务。

### Q8：用户可见信息

结论：默认展示当前阶段、正在修正的问题、剩余次数和下一步；可展开查看错误证据、修改差异、工具调用与验证结果。

理由：减少界面负担，同时保留可检查的行为记录与决策依据。

## 已批准的实施计划

1. 实现平台统一分流：候选可修错误、资料缺失、依据冲突、平台故障和无法判定分别处理；不把未知错误默认交给代码重试。记录错误代码、执行证据、分流理由及恢复动作。未知单位须区分已有自定义声明、待用户确认的定义和平台读取故障。
2. 统一任务状态与额度账本：补充信息、派生、恢复均不得静默增加额度；连续同类错误、上限耗尽和平台故障按已确认规则停止，保留历史。
3. 实现集中补充与影响分析：展示缺失项；语义或契约改变时生成修订差异并等待确认，其他情况仅重新验证受影响阶段。
4. 调整界面：默认突出继续当前任务及下一步；将整套方案重新生成与局部修正明确分开，详细记录折叠展示。
5. 验收覆盖：候选语法错误可自动修正；缺失单位定义集中询问；公式与样例的有依据冲突不迎合答案；平台故障不消耗候选修正循环；补充后额度不重置；契约改变须派生确认；原步骤与保护条件不被删除。除程序测试外，使用真实 DSH 任务检查行为是否符合规则。

## 待定

无影响本轮方案的产品决策待定。具体错误代码映射、状态迁移和受影响阶段计算方式，在实施时结合现有代码设计并验证；无法提供充分分流证据时按 Q4 暂停。
