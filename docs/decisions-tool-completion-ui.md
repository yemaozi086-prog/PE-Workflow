# 缺失计算工具补齐：交互与批量生成决策

日期：2026-10-18。用户已确认下述产品决策并批准实施。使用方式、实现边界及验收记录见 [tool-completion.md](tool-completion.md)；讨论决策不等同于整条 Buck 链的工程验收。

## Q1：复用方案声明，区分验证依据

结论：自动带入方案中的公式、字段、单位、保护条件和适用假设，显示来源及确认状态；独立样例另列。缺少独立样例时保持未验证，不要求用户重复填写三个文本框。

理由：计算声明足以约束代码生成，但不等于独立正确性证明。平台应复用已有资料，集中询问真正缺失或冲突的信息。

## Q2：多选排队补齐

结论：提供缺失工具清单，允许选择多个步骤，由平台逐个生成和验证；某步缺资料时暂停该步，其他没有依赖阻塞的步骤可继续。候选集中供用户核对后明确注册，不自动运行工作流。生成前展示选中数量、各步骤及合计调用上限，沿用已有停止规则。

理由：避免用户为多节点方案反复打开同样的表单，同时保留每步可追溯性和明确调用预算。

## 沿用已有边界

- 不编造物理含义、单位、自定义定义或独立预期答案。
- 补充信息不增加调用额度；同类错误连续两次停止该步骤的自动修正。
- 已确认的公式、接口、约束发生变化时派生修订并重新确认；旧记录保留。
- 工具的代码生成依赖与运行时数值依赖不同；上游工具尚未实现，不应自动被判为下游公式代码无法生成。只有缺少必要声明、验证数据或其他真实前提时才阻塞。

## Q3：部分通过时的注册

结论：允许用户明确勾选并核对通过的候选后先注册，统一形成一个关联这些工具的派生方案；其余步骤保留待补充状态与诊断。检查通过不等于用户批准注册，不将整批标记为完成。

理由：单个步骤缺资料不应阻止其他已核对工具的使用，同时避免为每个工具产生一条独立方案分支，使多节点任务的进度难以理解。

## 已批准的实施范围

1. 后端从选定方案修订提取并冻结每步的公式、字段、单位、保护条件、假设与来源，生成可核对的补齐上下文；明确缺失项，不以通用占位文本冒充声明或验证依据。
2. 前端用缺失工具清单替代重复必填文本框，默认展示完成状态和下一步；声明与来源可展开检查，只对缺项或冲突要求补充。独立样例单独管理并标明验证范围。
3. 新增持久化补齐队列，逐步生成和验证，不自动注册。启动前显示选中步骤、每步及合计调用上限；恢复和补充不静默增加额度。区分候选可修错误、资料缺失、依据冲突和平台故障，保存各步诊断。
4. 集中核对候选，允许用户选中已核对的部分注册，并在一个派生方案中关联这些工具；保留剩余缺失步骤。处理重复提交、版本占用和中途失败，避免重复注册或错误地标记整批完成。
5. 使用原 Buck 12 步方案的冻结副本进行验收，保留原方案与旧失败记录；覆盖自动带入、真实缺项、逐步暂停、额度上限、部分注册和恢复。结构、样例验证与工程适用性分别标注，不自动运行或宣称整条 Buck 链已验证。
