# 自动修正、补充依据与恢复

实施日期：2026-10-18。决策来源见 `decisions-repair-orchestration.md`。

## 当前入口与范围

本次接入“从需求设计工作流”的方案、工具候选与接线阶段。旧版上传替换协调器 `automation.py` 仍保留自己的状态机，本次未把它改为同一分流器。不要把本次验收解释为所有智能体入口已经统一。

平台根据错误代码、受控执行与验证记录分流；模型的解释不能直接授权平台修改校验器。错误规则在 `backend/pe_workflow/repair_routing.py`，不只依赖提示词。

| 分流 | 行为 |
| --- | --- |
| 明确候选错误，如语法、冻结接口下字段读取或接线错误 | 使用剩余额度修候选；保留公式、保护条件与接口边界 |
| 未登记单位、缺少语义或声明冲突 | 保留任务，按自定义声明或方案修订路径补充，不通过追加代码调用解决 |
| 公式、样例或已确认契约需要改变 | 派生修订、展示变更路径，再确认；原任务保留 |
| 样例数值不一致，但错误归属不明确 | 暂停，展示输入、预期与实际，集中核对依据 |
| 平台异常或未知错误 | 停止自动修正；未知错误不默认认定为代码错误 |

数值不一致时，可保留待补充任务；若用户核对后提供依据并明确保留原公式、样例和接口，可通过 `review-evidence` 使用剩余调用检查候选。它不修改验收答案，不清除重复错误计数，也不保证候选一定能修正。计算本身失败的记录不能走这个数值核对入口。

未知单位优先沿用已有标准表与项目自定义表机制。已存在定义却读取失败，属于平台排查范围，不能要求模型随意换单位。

## 额度与修订

- `calls` 保留本阶段累计已用次数，追加批准只增加 `call_limit`，同时记录 `budget_history`。
- `remaining_calls` 由平台计算。回答补充问题不增加额度。
- `stage_budgets` 按 plan、bind、formula:步骤编号分别记账；修订及注册后派生保留原阶段账本，旧记录缺少账本时从已有计数保守恢复。
- 同类错误连续两次停止。明确批准追加调用后才重开修正批次。
- 不重新执行无关计算模块。单位扩展后的保留候选可重新验证，不调用模型；工作流接线仍需按确认方案校验。
- 用户主动“另起新方案（完整重新规划）”是独立操作；界面不再把它标为继续修复。

目前修订差异显示修改路径，完整内容可对照父方案与当前声明。没有实现通用的跨整个任务图增量缓存与逐字段验证缓存，也没有自动证明物理公式与独立样例谁正确。

## 界面

默认显示当前阶段、错误去向、原因、下一步和剩余次数。具体证据与完整记录折叠展示；补充按钮显示额度不会增加。资料暂时拿不到时可选择“保存待补充”，保留问题且不消耗调用。不能靠追加代码调用解决的问题不展示追加入口，后端也拒绝绕过调用。
