# 从已确认方案补齐计算工具

## 使用方式

打开“从需求设计工作流”，恢复已有方案。通过接线预检查后，方案上方显示“补齐计算工具”。

1. 选择本轮缺失步骤；展开即可核对已采用的公式、字段、单位、假设、保护条件及来源。已有内容不再要求手写。
2. 只填写实际缺失的公式或来源说明。若缺少字段语义或需要修改现有接口，则派生修订后重新确认。原始函数上传保留在高级单步入口。
3. 独立样例单独添加。运行参数不是生成方案的必填项；缺少独立样例时，候选明确保持未验证。
4. 核对所选数量、每步及合计调用额度，明确确认后启动队列。首次生成计入上限；继承已有额度，不静默补满。
5. 平台按配置并发生成和验证（1–10，默认 2，平台总上限 10）；各步单独保留状态、额度与诊断。旧队列保持原并发数，缺资料时暂停受影响步骤。暂停后续步骤不会撤回已送达的调用。服务重启或送达不明不自动重发。
6. 本轮停止后核对代码与验证范围，勾选要注册的候选并明确确认。一次注册形成一个派生方案，未注册步骤继续保留。注册不运行工作流。
7. 部分注册后仍可在原队列核对其他候选；打开派生方案也能恢复相同队列。已选步骤全部注册后，可从派生方案选择下一批尚未排队的缺失步骤。

## 实现边界

- 后端 `tool_completion.py` 从方案生成确定的上下文，不让模型猜测这些既有声明。前端清单负责选择和核对；旧版手写入口保留作高级操作，并自动带入已有内容。
- `tool_completion_queues` 持久保存冻结来源、步骤任务、额度与注册收据。各步骤复用原有公式任务的检查、澄清、修正和自定义单位申请机制。
- 代码生成依赖与数值运行依赖分开处理：上游代码尚未实现，不妨碍已声明清楚的下游公式生成；独立样例必须提供该步骤实际需要的输入，不能把候选自己的输出当作独立答案。
- 注册采用单个 SQLite 事务，原子写入模块版本、版本关系、一个派生方案及注册收据。版本冲突整体回滚；重复提交相同注册请求返回原收据。
- 同一工具家族的多个派生候选预留不同版本号，生成时严格采用平台给出的目标版本，父版本关系独立保留。预留不等于发布，未注册候选可能造成可见版本号不连续；不会覆盖旧版本。
- 修改已确认公式不允许藏在队列补充中。明确的缺项补充保存在冻结副本，原方案不改变。改变公式、接口或约束仍需派生确认；不会自动替换其他已确认步骤。
- 结构检查、给定数值样例通过、工程适用性分别标注。队列既不自动选型，也不自动执行 Buck 全链或优化。

## 接口

- `GET /api/workflow-designs/{id}/tool-completion`：自动采用的声明、缺项、已有额度及可恢复队列。
- `POST /api/workflow-designs/{id}/tool-completion`：确认冻结来源修订、选中步骤及调用上限，创建幂等队列。
- `GET /api/tool-completion-queues/{id}`：各步骤进度、候选与验证范围。
- `POST /api/tool-completion-queues/{id}/pause`、`resume`：暂停或恢复后续步骤，不追加额度。
- `POST /api/tool-completion-queues/{id}/register`：明确选择并核对后部分注册。

请求模型以 `backend/pe_workflow/models.py` 为准。API 会拒绝过期修订、重复步骤、改写已有公式、静默重开同一步骤及不完整验证样例。
